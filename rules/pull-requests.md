# Pull Request Guidelines

## Workflow

1. Check `.github/PULL_REQUEST_TEMPLATE.md` if it exists.
2. Read the repository's `AGENTS.md`, `CONTRIBUTING.md`, and relevant bot instructions before reviewing or drafting.
3. For a review, inspect the diff together with the PR timeline, commits, reviews, inline comments, requested changes, and checks.
4. Default to read-only: reviewing does not authorize posting comments, requesting changes, approving, editing, pushing, or merging.
5. For a re-review, start from the previous review and classify each requested change as addressed, partial, unresolved, or obsolete.
6. Draft comments before posting. Prefer concise inline comments, avoid duplicates, show the exact draft, and wait for explicit approval.
7. Treat CodeRabbit, Copilot, CI, and other external feedback as evidence to verify, not authority.
8. Treat short follow-ups such as “go ahead” as authorization for the immediately discussed action only.
9. For a PR body or public reply, read the conversation first and remove context the recipient already knows, private reasoning, generic filler, and LLM-style prose.
## Formatting

- Do NOT repeat the title in the PR body (unless template requires it)
- Follow the style from user's previous PRs
- Keep it concise — match the complexity of the change
- Avoid LLM smells: no "This PR...", "This commit...", "This change...", filler words, emojis, excessive **bold**, over-explaining implementation details
